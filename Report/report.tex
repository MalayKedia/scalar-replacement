\section{What are we doing?}
\textbf{Scalar replacement}\\
Scalar replacement is an optimization technique where we replace an object with its individual fields and also convert any function calls with that object as the reciever to static calls. This is done to reduce the number of heap accesses and allocations, which are expensive operations. But this optimization is a per object optimization which is only possible under very specific conditions.These conditions are 
\begin{itemize}
    \item there is no instance in which there is a local variable which may point to this object and some other object.
    \item there is no instance in which there is a global variable which may point to this object.
    \item there is no instance in which there is a field which may point to this object.
    \item there is no instance in which it is passed as an argument to a method which changes the state of the object.
    \item It does not escape the method in which it is created.
    \item It never has its identity used in any way, for example, it is never compared with another object using == or it is never used as a key in a hash map.
\end{itemize}

Rather than trying five or six different optimizations each in a shallow way, we chose to go deep on one. Most of our time was spent on soundness: making sure every allocation we scalar-replace is one that's safe to
replace, and that the rewritten code is semantically equivalent to the
original. We have tried to be complete in our implementation, and we have not left any corner cases unhandled. We have also decided to be conservative in our implementation, and would rather miss some opportunities for scalar replacement than to perform an unsafe optimization.

\section{What analysis did we use?}

The tool is a three-pass pipeline registered on Soot's whole-program \texttt{wjtp} pack.

\textbf{Pass-1: per-method summaries}: For every user method we run a forward
dataflow that tracks, for each local, which of the enclosing method's
parameters it may directly alias. From that we derive a `MethodSummary`:
which parameters escape (return, throw, stored to static or to another
object's field), which are used for identity (`==`, `!=`, `instanceof`,
`synchronized`), which are forwarded to callees whose parameters are
themselves bad, which fields of each parameter are read, and which are
written. A caller checks the method summary to determine if it can scalar-replace an argument. Pass 1 runs in reverse topological order of the call-graph SCCs
computed by Tarjan, with pessimistic handling of cycles: every method in a
non-singleton SCC is marked fully bad and stays that way.

\textbf{Pass-2: per-allocation replaceability}: For each method we run a
second forward dataflow, this time tagging each local with the set of
allocation sites it may alias. When the alloc is used as the base of a
field access we record the field in the allocation's \texttt{fieldsUsed} set; when
it's passed to an invoke we consult the callee's summary and either accept
the call (good callee with empty modified-field set — we'll specialize it
later) or disqualify the alloc. Identity use, heap-store on the alloc's
ref, ambiguous aliasing (the local may refer to multiple allocations), and
passing to a mutating callee are disqualifiers.

\subsection{Pointer analysis: dimensions of precision}

Both passes are may-alias forward dataflow analyses. Our analysis is Flow-sensitive, Path-insensitive and Context-insensitive. Beyond that, some other features of our analysis are:

\begin{itemize}
    \item \textbf{Interprocedural via method summaries}: at a call site
    the forward dataflow queries the callee's previously-computed
    \texttt{MethodSummary} to decide how the call affects the caller's
    aliases.
    \item \textbf{Field-sensitivity}: partial. \texttt{readFields} and
    \texttt{modifiedFields} in \texttt{MethodSummary} track individual
    \texttt{SootField}s, so we
    know \emph{which} fields a callee reads vs.\ writes on a given
    parameter. The abstract state itself, however, does not model the
    heap: we do not track what's in $o.f$ for any abstract object $o$.
    So Pass 1 is field-sensitive for reads and writes on
    parameters but heap-insensitive for objects we don't control.

    \item \textbf{Allocation-site sensitive}:In Pass 2
    every \texttt{new} statement is its own abstract object, so two
    \texttt{new X()} at different source lines in the same method are
    distinct allocations with independent verdicts and independent
    scalar expansions. Arrays are never tracked.

    \item \textbf{Object-insensitive}: we don't refine summaries by
    dynamic type and we don't do heap cloning. For virtual dispatch we
    take the pessimistic union over all CHA/SPARK targets: a call is
    specialisable only if \emph{every} possible concrete callee is
    specialisable at that position.
\end{itemize}

\section{How do we transform the code?}

\textbf{Pass-3: IR rewrite.} For every surviving allocation we create
one fresh local per accessed field, named
\texttt{srO<line>\_<idx>\_<field>}. Before the
inlined constructor runs we splice in default-value writes to each of
these scalars (zero/null/false) so reads that precede an explicit
write behave like a freshly-allocated heap object.

The constructor chain (validated by Pass 2 to be well-behaved) is then
inlined at the allocation site by \texttt{InitInliner}. For each level
of the chain we clone every local with the unique name
\texttt{sr\_il<counter>\_<origName>}. Identity statements for
\texttt{@this} are dropped; \texttt{@parameterN} becomes a direct
\texttt{local = actual} binding; a \texttt{this.f = v} store in the
constructor becomes \texttt{sr\_f = v}; a super-\texttt{<init>} call
on \texttt{this} is replaced by a \texttt{NopStmt} and the recursion
splices the super's translated body in its place. Every dropped
statement leaves a \texttt{NopStmt} placeholder. The
\texttt{new X;} and the original \texttt{<init>} call are deleted and
insertion is just before the \texttt{<init>} invoke.

After the alloc-site rewrite we walk the rest of the caller body:
every field access whose base unambiguously aliases a scalar-replaced
allocation (per Pass 2's flow-sensitive \texttt{AllocState}) is
redirected to the matching scalar local.

Non-\texttt{<init>} calls receiving the allocation become staticinvokes
of a synthesised specialisation produced by \texttt{Specializer}. The
specialisation is keyed on \texttt{(callee, set of scalarised
positions)}. Its name is
\texttt{<origName>\$scalar\_<positions>} (e.g.\
\texttt{foo\$scalar\_0\_1}). Each scalarised reference parameter in the
signature expands into one primitive/ref parameter per field the callee
reads, named \texttt{srP<pos>\_<field>}; non-scalarised
parameters pass through unchanged. We clone the body with
\texttt{Body.importBodyContentsFrom}, rewrite \texttt{@this}/\texttt{@parameter} identity
statements to match the widened signature, replace field reads on
aliases of the scalarised parameter with reads of the corresponding
\texttt{srP} local, and recursively specialise any nested invoke
that forwards a scalarised parameter.


\section{Partial scalar replacement: what we tried and why we dropped it}

The obvious next step after "kill allocations that don't escape" is "kill
allocations that only escape on some paths". If an object leaks into the
heap only inside an if branch that's rarely taken, we'd rather keep the
scalars on the hot path and materialize a real object just before the escape.

Where we came unstuck was generalising the soundness conditions. The
easy cases — single escape point on a branch, no post-escape field writes,
simple constructors without static side effects — were clean. But as soon
as we tried to combine them (multi-escape paths, control-flow joins where
some predecessors had materialized and some hadn't, constructors with
\texttt{counter++} style side effects that would double-execute if we called
\texttt{<init>} at materialization) we ran into cases where a particular design
choice was either too strict (giving up on obviously-safe cases) or too
loose (producing semantically wrong output on testcases we couldn't
enumerate in advance). We got to a point where each fix for one shape
reintroduced a failure on another.
